# Native Pi slice: scope before implementation

**TARGET — user-authorized continuation, 2026-09-11:** build the next native adapter from the proven Pi callback seam. Keep the real Pi loop, original tool definitions, Webdesk RPC/supervisor and supervised approval policy. Use the existing Trialyard v1 process protocol, native bundles and verifier. Keep the local scripted provider and the preregistered two-turn/fresh-repeat, denied-write and interrupted-write fixtures; no paid model calls, Webdesk source changes, daemon/UI workflows or milestone-completion claims.

**TARGET — accounting:** an extension's pre-tool hook first waits for the native runner's tool intent. Original Webdesk policy then allows or denies. Only an allowed callback may ask the environment for a durable dispatch-observation acknowledgment and then call the original implementation. A denial becomes `not_dispatched`; it never receives an invented dispatch observation. Model operations account for entry into the explicit local scripted responder and retain actual Pi-bound context; this does not establish provider accounting or model quality. Missing token usage remains null.

**TARGET — packaging:** collect the installed Pi pnpm dependency graph, pin compressed package bytes as ordinary native artifacts, validate expansion paths/links/size, and extract only inside an owned fresh lease. Test a relocated build without consulting the original installation at runtime. Preserve dependency bytes and package layout; document platform prerequisites. Do not raise native inventory limits or present compression as build attestation.

**TARGET — checks:** contract fixtures and duplicate/failure tests first; actual native runs and verifier checks next. Require distinct leases/sessions, model-bound follow-up history, independent files read before and after interruption, denied dispatch with absent file, observed process cleanup and explicit unknown outcomes. Also reject tampered packaged inputs and prevent replay under a repeated request identity. Preserve failed attempts and unresolved limitations. M3 human onboarding, M4 consumer and full M5 broader reuse remain separate gates.
